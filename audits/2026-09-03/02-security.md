## Findings

### F01. [Medium] Chrome is launched with `--no-sandbox` unconditionally, in a library whose purpose is visiting untrusted sites — src/pyutilz/web/browser.py:322
- **Disposition**: OPEN
- **Category**: browser-sandbox-disabled
- **Problem**: `start_selenium()` adds `options.add_argument("--no-sandbox")` on every code path, for every caller, on every platform. The line is preceded only by a commented-out `# if not undetectable:` (src/pyutilz/web/browser.py:321), so there is no flag, kwarg, or environment condition that turns it back on. This is the same function that immediately below deliberately hardens the CDP surface (`--remote-debugging-port=0`, `--remote-debugging-address=127.0.0.1`, src/pyutilz/web/browser.py:331-332), so the security posture inside one function is inconsistent. The module's proxy-rotation/`handle_blocking` machinery (`src/pyutilz/web/web/fetching.py:353-362`) makes clear the browser is pointed at arbitrary third-party sites.
- **Failure scenario**: A scraped page serves a renderer exploit (a malicious ad, a compromised CDN script, a hostile SVG/WASM payload). With the sandbox enabled, the exploit is confined to a low-privilege renderer process. With `--no-sandbox`, renderer-process code execution IS code execution as the scraper's OS user — which on a typical deployment of this library also holds the S3 credentials read by `connect_to_s3()`, the DB DSN, and the proxy credentials.
- **Suggested fix**: Drop the unconditional `--no-sandbox` and add it only under an explicit opt-in parameter (e.g. `no_sandbox: bool = False`) documented as "required only for running as root inside a container; disables Chrome's process sandbox". If a containerised caller genuinely needs it, the correct fix there is a non-root container user plus an appropriate seccomp profile, not disabling the sandbox for every consumer of the library.

### F02. [Medium] Proxy host/port/user/password are interpolated unescaped into the JavaScript source of a privileged Chrome extension — src/pyutilz/web/browser.py:256-285
- **Disposition**: OPEN
- **Category**: code-injection
- **Problem**: `background_js` is a `"""..."""  % (...)` template (src/pyutilz/web/browser.py:256-285) whose four `%s` placeholders sit inside JavaScript string literals: `host: "%s"`, `port: parseInt(%s)`, `username: "%s"`, `password: "%s"`. The substituted values come straight from `proxy_server["PROXY_HOST"]`, `["PROXY_PORT"]`, `["PROXY_USER"]`, `["PROXY_PASS"]` with no escaping, quoting, or validation of any kind — the only checks upstream are presence checks (src/pyutilz/web/browser.py:227-233). The resulting script is zipped into an extension (src/pyutilz/web/browser.py:309-311) declaring `webRequest`, `webRequestBlocking`, `tabs`, `storage` and `<all_urls>` permissions (src/pyutilz/web/browser.py:240-247) — the most privileged JS context in the browser.
- **Failure scenario**: Two distinct outcomes. (a) Benign but silent: a proxy password containing a `"` or a backslash — legal in a proxy password and common in generated credentials — produces syntactically broken JS, the extension fails to register `onAuthRequired`, and every request goes out un-authenticated to the proxy, which the caller sees only as unexplained 407s. (b) Injection: a proxy entry sourced from a rotating-proxy vendor's API response, a config file, or a DB row whose password field is `x"};alert(1);var y={"a":"` yields arbitrary JavaScript executing in an extension context with `<all_urls>` blocking `webRequest` — i.e. able to read and rewrite every request/response of the authenticated scraping session, including cookies.
- **Suggested fix**: Build the values with `json.dumps()`, which emits a correctly escaped JS/JSON string literal for any input: `host: %s` with `json.dumps(proxy_server["PROXY_HOST"])`, and likewise for user/password; use `port: %d` with `int(proxy_server["PROXY_PORT"])` so a non-numeric port fails loudly rather than being spliced into `parseInt(...)`.

### F03. [Medium] Caller-supplied request headers (API keys, `Authorization`) are forwarded verbatim to cross-host redirect targets — src/pyutilz/web/url_guard.py:84 (reached from src/pyutilz/web/cached_client.py:135)
- **Disposition**: OPEN
- **Category**: credential-leak
- **Problem**: `urlopen_checked` builds its opener with `_CheckedRedirectHandler`, which overrides `redirect_request` only to re-check the *scheme* and then delegates to `super().redirect_request(...)` (src/pyutilz/web/url_guard.py:61-66). CPython's `HTTPRedirectHandler.redirect_request` copies every header off the original `Request` onto the new one, stripping only `content-length` and `content-type` — confirmed by reading `inspect.getsource(urllib.request.HTTPRedirectHandler.redirect_request)` on the installed 3.11.5: `newheaders = {k: v for k, v in req.headers.items() if k.lower() not in CONTENT_HEADERS}`. It performs no host comparison. `CachedHttpClient._fetch_bytes` constructs exactly such a header-bearing `Request` from its caller's `headers=` dict (src/pyutilz/web/cached_client.py:135) and hands it to `urlopen_checked` (src/pyutilz/web/cached_client.py:139). The `url_guard` module docstring scopes host/IP filtering out explicitly, but says nothing about header propagation, so a caller reasonably reads "checked" as covering this.
- **Failure scenario**: A caller does `client.get_json(url, tag, headers={"Authorization": "Bearer <api-token>"})` against a third-party API. That API (or a compromised/expired domain it redirects through, or an operator-controlled shortener in the URL) answers `302 Location: https://attacker.example/...`. The scheme is `https`, so `_CheckedRedirectHandler` allows it, and urllib re-sends the `Authorization` header to `attacker.example`. The token is disclosed with no error and no log line.
- **Suggested fix**: In `_CheckedRedirectHandler.redirect_request`, after computing the delegated `Request`, drop sensitive headers when `urlsplit(newurl).netloc` differs from `urlsplit(req.full_url).netloc` — at minimum `Authorization`, `Proxy-Authorization`, `Cookie`, and any header the caller marks sensitive. Document the behaviour in the module docstring alongside the existing host-filtering scope note.

### F04. [Medium] `logged()` persists every string/number kwarg and the raw exception text to a DB table with no redaction — src/pyutilz/dev/logginglib.py:382, :408 (persisted at :233-236)
- **Disposition**: OPEN
- **Category**: credential-logging
- **Problem**: Two separate unredacted sinks into the same persisted row. (1) `results_log["parameters"]` is built as `{key: value for key, value in params.items() if key not in special_vars}` (src/pyutilz/dev/logginglib.py:382), where `special_vars` is the fixed 3-tuple `("current_proxy", "current_proxy_resolved", "login")` (src/pyutilz/dev/logginglib.py:356). Every *other* argument that survives the `allowed_types=(numbers.Number, str)` filter is stored verbatim — a `password=`, `api_key=`, `token=`, or `dsn=` kwarg is captured in full. The 2026-09-02 wave hardened the three named `special_vars` via `_redact_credential_shaped_value` but left the general `parameters` bucket untouched. (2) `results_log["results"]["error"] = f"{type(exc).__name__}: {exc}"` (src/pyutilz/dev/logginglib.py:408) stores raw exception text. `finalize_function_log` then writes both columns into `db_path` with `json_pg_dumps` (src/pyutilz/dev/logginglib.py:232-236), or prints the whole dict when `verbose` (src/pyutilz/dev/logginglib.py:239). The repo already ships the exact tool for sink (2): `pyutilz.text.secrets_scrub.redact_secrets`, whose own docstring calls itself "the general-purpose ... scrubber for log lines and values about to be persisted" (src/pyutilz/text/secrets_scrub.py:15-18). It is not called from `logginglib.py` at all.
- **Failure scenario**: A `@logged(db_path="logging.api_calls")`-decorated function raises `psycopg2.OperationalError` on connect. psycopg's message embeds the full DSN including the password; that string lands verbatim in the `results` JSONB column of a long-lived log table, readable by everyone with read access to the logging schema and by anything that later exports it. Independently, any decorated function taking a `token=`/`password=` string parameter has that value written to the `parameters` column on every single call, success or failure.
- **Suggested fix**: Wrap the error string with `redact_secrets(...)` at src/pyutilz/dev/logginglib.py:408, and run `parameters` values through the same scrubber (or add a name-based credential filter reusing `dev/code_audit/credential_logging.py`'s `_CREDENTIAL_NAME_RE`) before assigning at src/pyutilz/dev/logginglib.py:382, so the named-`special_vars` protection generalises instead of enumerating three names.

### F05. [Medium] The canonical secret scrubber misses quoted/JSON key-value shapes and suffixed env-var names, passing them through in full — src/pyutilz/text/secrets_scrub.py:82
- **Disposition**: OPEN
- **Category**: credential-logging
- **Problem**: `SECRET_KEY_VALUE_RE` (src/pyutilz/text/secrets_scrub.py:82) is `(?i)(password|passwd|api[_-]?key|token|secret|authorization|auth)\s*[:=]\s*(?!(?:Bearer|Basic)\b)\S+`. Two structural gaps, both confirmed by running `redact_secrets` on the installed interpreter against the current source: (a) the separator alternation `\s*[:=]` requires the keyword to be *immediately* followed by the separator, so a quoted key never matches — `redact_secrets('{"password": "s3cret", "api_key": "sk-abc"}')` returns the input **unchanged**, because the `"` sits between `password` and `:`. This covers JSON bodies, Python `repr()` of a config dict, and TOML/YAML quoted keys. (b) the keyword must be the whole token before the separator, so a name with a suffix escapes — `redact_secrets('AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI')` also returns the input **unchanged** (`SECRET` is followed by `_ACCESS_KEY`, not `=`; the `api[_-]?key` alternative requires a literal `api` prefix). The module bills itself as "the one place new secret shapes get added going forward, for every downstream project" (src/pyutilz/text/secrets_scrub.py:7-8), and `dev/code_audit/registry.py:150-166` designates it as the canonical scrubber that the `duplicate_credential_regex` scanner steers downstream projects toward — so these gaps propagate by design.
- **Failure scenario**: A downstream service follows the documented guidance and routes an HTTP error body through `redact_secrets` before writing it to its error log. The upstream API answers `400 {"error":"bad credentials","api_key":"sk-live-..."}` — the echoed live key is written to the log verbatim, and the developer has positive reason to believe it was scrubbed. Same for any `env`-style diagnostic dump containing `AWS_SECRET_ACCESS_KEY=` or `GITHUB_TOKEN_FOR_CI=`.
- **Suggested fix**: Widen the key side to tolerate a quote and a surrounding identifier: allow an optional `["']` between the keyword and the separator, allow a leading/trailing word-character run around the keyword (`[A-Za-z0-9_]*(?:secret|token|password|api[_-]?key)[A-Za-z0-9_]*`), and make the value alternation accept a quoted run (`"[^"]*"|'[^']*'|\S+`) so the closing quote is consumed rather than left dangling. Add each of the two verified inputs above as a doctest/unit case so the gap cannot silently reopen.

### F06. [Medium] `_safe_parse` catches only `SyntaxError`; a valid-but-deeply-nested source file raises `RecursionError` out of `ast.parse` and aborts the whole scan — src/pyutilz/dev/code_audit/_base.py:128-131
- **Disposition**: OPEN
- **Category**: denial-of-service
- **Problem**: `_safe_parse`'s contract, stated in its own docstring, is "returning None on read failure (I/O, decode) or a syntax error instead of raising" (src/pyutilz/dev/code_audit/_base.py:109). Its handlers are `except (OSError, UnicodeDecodeError)` around the read (src/pyutilz/dev/code_audit/_base.py:125) and `except SyntaxError` around the parse (src/pyutilz/dev/code_audit/_base.py:130). `ast.parse` on a syntactically valid file with a deep left-nested expression raises `RecursionError`, which is neither. Verified on the installed Python 3.11.5 against the current tree: a one-line file containing `return a + a + ...` (5000 terms) produces `RecursionError: maximum recursion depth exceeded during ast construction` propagating out of `_safe_parse` at `_base.py:129`, and out of `run_all(Path(...), checks=[...])` to the caller — the whole scan dies, no findings are returned, and no file is skipped or reported. For contrast, 600 nested parentheses *is* a `SyntaxError` in 3.11 and is handled correctly, and 400 `+` terms scans cleanly, so the failure is specific to depth, not size.
- **Failure scenario**: The package is explicitly "designed to be run against any Python source tree, not just pyutilz" (src/pyutilz/dev/code_audit/cli.py:57-59) and `run_all` is wired into pre-commit as a blocking gate (`.pre-commit-config.yaml:92`, `:103`). A single machine-generated file — a large generated parser table, a `.py` fixture with a long literal concatenation, an auto-generated protobuf/constants module, or a file deliberately planted in a repo under review — makes every scan of that tree crash with a traceback, rather than skipping the one file. Under the `ProcessPoolExecutor` path this surfaces as an opaque worker death instead of a named file.
- **Suggested fix**: Add `RecursionError` (and `MemoryError`, the same class of parser-resource failure) to the `except SyntaxError` clause at src/pyutilz/dev/code_audit/_base.py:130, caching and returning `None` exactly as for a syntax error, and log the skipped path at debug so a silently-unscanned file is still traceable.

### F07. [Low] `CachedHttpClient` reads an entire remote response into memory with no size cap — src/pyutilz/web/cached_client.py:141
- **Disposition**: OPEN
- **Category**: denial-of-service
- **Problem**: `_fetch_bytes` does `return cast(bytes, resp.read())` (src/pyutilz/web/cached_client.py:141) with no `amt` argument and no `Content-Length` check; the bytes are then decoded and written into the on-disk cache (src/pyutilz/web/cached_client.py:112-114). The module's own threat model already treats the remote server as hostile — `MAX_RETRY_AFTER_SECONDS` exists precisely because "`Retry-After` is attacker/remote-controlled" (src/pyutilz/web/cached_client.py:32-36) — so an unbounded read from the same untrusted party is an inconsistent gap rather than an accepted risk.
- **Failure scenario**: A hostile or merely broken endpoint answers a `get_json()` with a multi-gigabyte chunked body (or an effectively infinite stream). The calling thread allocates until the process is OOM-killed, or fills the cache volume; the per-host throttle and the retry cap provide no protection because the failure is inside a single successful response.
- **Suggested fix**: Add a `max_bytes` parameter (a sane default in the tens of MB) and read in a bounded loop, aborting with a logged warning once the limit is passed; reject up front when `resp.headers.get("Content-Length")` already exceeds it.

### F08. [Low] External binaries are spawned by bare name, and Windows `CreateProcess` searches the current directory before `PATH` — src/pyutilz/system/system/probing.py:592, src/pyutilz/system/system/sysinfo.py:147, :161, :164
- **Disposition**: OPEN
- **Category**: binary-planting
- **Problem**: Four `subprocess` call sites pass an unqualified executable name: `["nvidia-smi", "-q", "-x"]` (src/pyutilz/system/system/probing.py:592-597), `["getprop", "ril.serialnumber"]` (src/pyutilz/system/system/sysinfo.py:147), `["ioreg", "-rd1", "-c", "IOPlatformExpertDevice"]` (src/pyutilz/system/system/sysinfo.py:161) and `["grep", "-E", "(UUID)"]` (src/pyutilz/system/system/sysinfo.py:164). Each carries a `# nosec B603 B607` justification arguing the binary is "fixed trusted" — true of the *name*, but not of the *resolution*. With `shell=False` and no `lpApplicationName`, Windows' `CreateProcess` search order places the current working directory ahead of the `PATH` directories, so `nvidia-smi` resolves to an `nvidia-smi.exe` sitting in the process's cwd if one exists. The `nvidia-smi` path is the reachable one on Windows and is called from GPU probing, which this package runs early and broadly. The identical class was already fixed once in this repo for `pip` (`ensure_installed` now uses `sys.executable -m pip`, src/pyutilz/core/pythonlib/packages.py) — the fix simply was not generalised.
- **Failure scenario**: A user runs a pyutilz-based script with the cwd set to a shared or downloads directory (or any directory another local account can write). An attacker-planted `nvidia-smi.exe` there executes with the user's privileges the first time GPU probing runs, before `PATH`'s real `nvidia-smi` is ever consulted.
- **Suggested fix**: Resolve each name once via `shutil.which(...)` and pass the absolute path to `subprocess`, raising or skipping the probe when `which` returns `None` (this also replaces the current `FileNotFoundError` handling with an explicit check). Update the `nosec` justifications to say "absolute path resolved via shutil.which", which is the claim that actually holds.

### F09. [Low] Reusable workflows are pinned to a mutable `@v1` tag while every third-party action in the same files is SHA-pinned — .github/workflows/ci.yml:123, :129, :141; .github/workflows/black-filtered.yml:20; .github/workflows/docs.yml:33; .github/workflows/mypy-full.yml:28
- **Disposition**: OPEN
- **Category**: supply-chain
- **Problem**: Every third-party action reference in these workflows is pinned to a full commit SHA with a version comment — `actions/checkout@3d3c42e5...  # v7.0.1`, `actions/setup-python@5fda3b95...`, `actions/upload-artifact@043fb46d...`, `pypa/gh-action-pypi-publish@dc37677b...` — and even the composite action from the *same* owner is SHA-pinned (`fingoldo/py-ci-shared/.github/actions/upload-codecov@f50288e5a6f5b7f972efb60f948ce6184c8e9e70  # v1.3.4`, .github/workflows/ci.yml:94). The six *reusable-workflow* references to that same repository are not: they use the floating tag `@v1` (.github/workflows/ci.yml:123, :129, :141; .github/workflows/black-filtered.yml:20; .github/workflows/docs.yml:33; .github/workflows/mypy-full.yml:28). `.pre-commit-config.yaml:266-267` likewise pins `fingoldo/py-ci-shared` by `rev: v1.2.1`, a mutable tag. A `v1` tag is designed to be moved.
- **Failure scenario**: If the `py-ci-shared` repository or the account is compromised, moving the `v1` tag silently changes the code every pyutilz CI run executes — including the `docs.yml` leg, which runs with `pages: write` and `id-token: write` (.github/workflows/docs.yml:26-29). ### F10. [Low] Dependabot's pip ecosystem is disabled, so no Python dependency security updates are proposed — .github/dependabot.yml:26-38
- **Disposition**: OPEN
- **Category**: supply-chain
- **Problem**: The `pip` ecosystem block sets `open-pull-requests-limit: 0` (.github/dependabot.yml:29), documented as "Temporarily disabled 2026-07-10" for GitHub Actions-minutes budget reasons (.github/dependabot.yml:17-25). It has been off for roughly two months as of this audit. The `github-actions` ecosystem remains active. Every runtime dependency in `pyproject.toml` is declared with an open lower bound (`numpy>=1.20`, `joblib>=1.2`, `requests>=2.28`, `selenium>=4.0`, `boto3>=1.26`, and around forty more), so there is no lockfile to audit either — nothing in the repository tracks which versions a security advisory would affect.
- **Failure scenario**: A CVE lands in a declared dependency (the `web` extra alone pulls `requests`, `selenium`, `undetected-chromedriver`, `curl-cffi`, `grequests`). No PR is opened, no CI signal appears, and because the constraints are open-lower-bound with no lockfile, nothing in the repo records exposure — the vulnerability is noticed only if a maintainer reads advisories by hand.
- **Suggested fix**: The Actions-minutes tradeoff is legitimate, so rather than simply re-enabling, restore a *signal* without the CI cost: enable GitHub's Dependabot **security** alerts/updates (which fire only on advisories, not on routine version bumps) while leaving version updates at limit 0, or add a scheduled `pip-audit` job that runs weekly on `ubuntu-latest` only. Record the choice in `.github/dependabot.yml` next to the existing comment so the disable stops reading as unbounded.

### F11. [Low] LLM API keys are loaded from a `.env` resolved relative to the process working directory — src/pyutilz/llm/config.py:20
- **Disposition**: OPEN
- **Category**: credential-handling
- **Problem**: `LLMSettings.model_config` sets `env_file=".env"` (src/pyutilz/llm/config.py:20) — a bare relative filename, which pydantic-settings resolves against the current working directory at instantiation time, not against the importing package or a caller-specified root. `get_llm_settings()` re-instantiates `LLMSettings()` every `_SETTINGS_TTL_SECONDS` (default 60s, src/pyutilz/llm/config.py:39, :57), so the file is re-read periodically and the effective credential can change if the process `chdir`s. Nothing documents the cwd dependency; the module docstring says only "Reads API keys from environment variables / .env files" (src/pyutilz/llm/config.py:3).
- **Failure scenario**: A user runs a pyutilz-based tool from a directory they do not control — a cloned third-party repo, a shared scratch directory, an extracted archive — that contains its own `.env`. For any provider key not already set in the real environment (pydantic-settings gives process env vars precedence over the `.env` file, so this is the unset-key case), the planted value is silently adopted and every subsequent LLM call is billed to, and its prompts sent under, an attacker-chosen key. There is no log line naming which file was loaded.
- **Suggested fix**: Make the `.env` location explicit — accept a path parameter on `get_llm_settings()` (defaulting to an anchor the caller controls, or to `None` meaning env-vars-only), and log at INFO which `.env` path was actually read when one is found, so an unexpected file is visible rather than silent.

### F12. [Low] `unserialize()` calls `zlib.decompress` with no output bound — src/pyutilz/core/serialization.py:152
- **Disposition**: OPEN
- **Category**: denial-of-service
- **Problem**: `data = zlib.decompress(obj)` (src/pyutilz/core/serialization.py:152) is called with no `bufsize`/`max_length` and no incremental decompression, so the decompressed payload is materialised in full regardless of size. The surrounding function accepts a file path, raw bytes, or a file-like object (src/pyutilz/core/serialization.py:98) and the compression step is on by default (`compression: Optional[int] = 9`). The function's optional sidecar verification (`verify_sidecar=True`, src/pyutilz/core/serialization.py:135-146) runs *before* this point and would catch a tampered file — but it defaults to `False`, and it does not apply at all to the bytes/file-like input path (documented at src/pyutilz/core/serialization.py:115-117).
- **Failure scenario**: A caller feeds `unserialize()` bytes obtained from a cache, a message queue, or a file it did not author. A few-kilobyte zlib bomb expands to gigabytes inside `zlib.decompress` before `pickle.loads` is ever reached, exhausting memory. The pickle risk itself is separately gated by the sidecar mechanism; the decompression happens first and is not.
- **Suggested fix**: Use a `zlib.decompressobj()` with `decompress(data, max_length=...)` in a loop against a caller-configurable ceiling, raising a clear error when the ceiling is passed — the same shape as the `MAX_RETRY_AFTER_SECONDS` cap already used elsewhere in this codebase for a remote-controlled quantity.

### F13. [Low] The escaped-tool-use tripwire added to the Claude Code SDK path has no counterpart on the CLI path — src/pyutilz/llm/claude_code_provider.py:709-720
- **Disposition**: OPEN
- **Category**: defense-in-depth-asymmetry
- **Problem**: Both backends run with permissions bypassed (`permission_mode="bypassPermissions"`, src/pyutilz/llm/claude_code_provider.py:518; `--dangerously-skip-permissions`, src/pyutilz/llm/claude_code_provider.py:621) and both disable tools the same way (`--tools ""` plus `--strict-mcp-config`).
