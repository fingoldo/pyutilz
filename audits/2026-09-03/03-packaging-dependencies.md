## Findings

### F01. [Medium] Two shipped, exported and unit-tested `code_audit` scanners are registered nowhere, so `run_all()` and the CLI never execute them — and one duplicates a registered module — src/pyutilz/dev/code_audit/registry.py:216
- **Disposition**: OPEN
- **Category**: dead-wiring-packaged-module
- **Problem**: Measured by importing the package and comparing `get_scanners()` (89 entries) against every `scan_*` in `__all__` (70), unwrapping `functools.partial`: `scan_assert_in_loop_reports_only_the_first` (`src/pyutilz/dev/code_audit/assert_in_loop.py:61`, exported at `__init__.py:524` and `__init__.py:618`) and `scan_reexport_patch_target` (`reexport_patch_target.py:92`, exported at `__init__.py:526` and `__init__.py:620`) never appear in `registry.py` — `grep -n "assert_in_loop\|reexport_patch_target" registry.py` returns nothing across all 379 lines. Both have the standard registrable signature (`(root, exclude_dirs, …) -> list[Finding]`), so neither is excluded for the documented reason `field_text_agreement` is (`__init__.py:443-453`, "a record-level checker cannot" honour `(root: Path, exclude_dirs)`), and neither is in `OPT_IN_ONLY` (15 names, enumerated at runtime). `tests/test_assert_in_loop.py` calls the function directly, so its unit tests pass while the pipeline never runs it. Separately, `reexport_patch_target.py` is a near-duplicate of `patch_target_is_a_reexport.py`, which IS registered (`registry.py:70` import, `registry.py:216` `register_scanner("patch_target_is_a_reexport", …)`); `git log` shows they landed in two different commits (`f990255` "two scanners for test-integrity bugs that pass silently", `2399920` "a check for a patch aimed at the wrong copy of a name") for the same defect class.
- **Failure scenario**: A downstream project runs `python -m pyutilz.dev.code_audit ./src` (the documented entry point) or `run_all(root)` and gets a clean report while the assert-in-loop and reexport-patch-target defect classes are silently unchecked — the checks exist, ship in the wheel, are described in `__init__`'s prose, are covered by tests, and cannot fire. Any project that committed a `_code_audit_baseline.json` believing those classes were gated holds an unearned clean bill of health.
- **Suggested fix**: Add `register_scanner("assert_in_loop_first_failure_only", scan_assert_in_loop_reports_only_the_first)` to `registry.py`; decide between `reexport_patch_target` and `patch_target_is_a_reexport` and delete the loser (or register both under distinct names if they genuinely differ). Then add a meta-test asserting every `scan_*` in `code_audit.__all__` is either in `get_scanners()` or in an explicit, reason-carrying `_DELIBERATELY_UNREGISTERED` map — the same allowlist shape `tests/test_meta/test_optional_deps_isolation.py:144`'s `_EXTRAS_WITHOUT_MASKING_SCENARIO` already uses for extras, so a newly added scanner cannot be forgotten the way these two were.

### F02. [Medium] `pytest-randomly` — declared a real requirement of the suite — is installed on none of the 21 CI legs, so test-order randomisation never runs in CI — .github/workflows/ci.yml:73
- **Disposition**: OPEN
- **Category**: ci-test-dependency-gap
- **Problem**: `requirements-dev.txt:16-24` declares `pytest-randomly>=3.12` and states its purpose verbatim: it "randomises test ORDER each run, which is what makes order-dependence (shared module state such as `pyutilz.llm.factory._provider_cache`, or a sys.modules stub leaking between files) actually surface", concluding "so it is a real requirement, not an optional nicety". `tests/conftest.py:33-81` ships a thinc/pytest-randomly seed-overflow compat shim built specifically for it, and `conftest.py:35-38` records that the plugin "IS installed and active in the reference environment (plugin banner shows `randomly-4.0.1`)". `grep -rn "requirements-dev" .github/` returns only two prose mentions inside `publish.yml:81,87` — **no workflow installs the file**. `ci.yml:73` installs `-e ".[pandas,polars,database,system,llm,nlp,cloud,speedups,dev]"`, `publish.yml:63` installs `-e ".[all,dev]"`, `numba-coverage.yml:64` and `mypy-full.yml:33` likewise — and `pytest-randomly` is deliberately absent from the `[dev]` extra (pyproject.toml:349-388 lists seven pytest plugins, not this one).
- **Failure scenario**: A module-state leak of exactly the kind named in `requirements-dev.txt` (`_provider_cache`, a `sys.modules` stub) is introduced. All 21 CI legs run the suite in fixed alphabetical order and pass; the defect surfaces only on a contributor's box that happened to run `pip install -r requirements-dev.txt`. The conftest shim, whose only reason to exist is a crash requiring the plugin to be present, is dead code on every CI leg.
- **Suggested fix**: Append `-r requirements-dev.txt` to the install step in `ci.yml:73` (and `publish.yml:63`), or move `pytest-randomly>=3.12` into pyproject.toml's `[dev]` extra — it has no direct-reference problem, unlike `py-ci-shared`, so the stated reason for co-locating it in `requirements-dev.txt` ("purely to keep this file the single place a contributor is told to install from") does not apply to CI. Add an assertion to `tests/test_meta/test_shared_checks_wired.py` that every non-VCS requirement in `requirements-dev.txt` is importable in the running environment, so this cannot silently regress.
