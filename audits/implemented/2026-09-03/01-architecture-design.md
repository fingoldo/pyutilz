## Findings

### F01. [High] The `unraised_exception_class` scanner emits `severity="Medium"`, a value outside the package's four-level convention, so the CLI silently discards every one of its findings — src/pyutilz/dev/code_audit/unraised_exceptions.py:139
- **Disposition**: COMPLETED — already fixed by the fa1aab0 wave: `SEVERITIES`/`severity_rank`/`UNKNOWN_SEVERITY_RANK` are the one vocabulary in `_base.py:41-51`, `Finding.__post_init__` (`_base.py:79`) rejects anything outside it, and an unknown severity now ranks ABOVE P0 so it renders and gates instead of being filtered away; no `severity="Medium"` remains in the package.
- **Category**: registry-consistency
- **Problem**: `_base.py:31` documents the convention as `P0/P1/P2/Low`, and both severity tables in the package (`cli.py:92` and `registry.py:357`) enumerate exactly those four keys with `.get(f.severity, 99)` as the fallback. `unraised_exceptions.py:139` is the only construction site in all 89 scanner modules that passes anything else: `severity="Medium"`. Verified by grep over every `severity="..."` literal in the package — 7 `P0`, 33 `P1`, 47 `P2`, 16 `Low`, and this one `Medium`. Because 99 is greater than every cutoff including `Low`'s 3, `cli.py:94` filters the finding out at *every* `--min-severity` setting, and `cli.py:100`'s exit-code gate only looks for `P0`/`P1`, so the check can never fail CI either.
- **Failure scenario**: writing `class NeverRaised(Exception): """doc"""` to `m.py` and running `python -m pyutilz.dev.code_audit . --check unraised_exception_class --min-severity Low` prints `_No findings._` and exits 0. The same tree through `run_all(root, checks=["unraised_exception_class"])` returns `[('Medium', 'unraised_exception_class', 'm.py', 1)]`. Both runs executed and confirmed. A downstream project running the CLI sees a registered, advertised check that reports nothing, ever.
- **Suggested fix**: change `severity="Medium"` to `severity="P2"` (an unraised exception class is design debt, not a live defect). Then add a meta-test that asserts every `Finding` any registered scanner produces over a fixture corpus carries a severity in `{"P0","P1","P2","Low"}` — or better, make `Finding.__post_init__` reject an unknown severity so a fifth level cannot be introduced silently again.

### F02. [High] Two scanner functions are exported from the package facade and its `__all__` but never registered, so `run_all()` and the CLI can never run them — src/pyutilz/dev/code_audit/__init__.py:524
- **Disposition**: COMPLETED — already fixed by the fa1aab0 wave: all 95 `scan_*` functions in the package are registered and facade-exported, pinned by `test_registry_and_facade_are_in_bijection` (verified live: zero unregistered scanners, zero names missing from `__all__`).
- **Category**: registration-discipline
- **Problem**: `scan_assert_in_loop_reports_only_the_first` (imported at `__init__.py:524`, in `__all__` at `:618`) and `scan_reexport_patch_target` (imported at `:526`, in `__all__` at `:620`) have no `register_scanner(...)` call anywhere; `registry.py` does not even import either module. Verified live: iterating `pkgutil.iter_modules` over the package finds 92 `scan_*` functions, and comparing against `get_scanners()` (89 entries) leaves exactly `scan_assert_in_loop_reports_only_the_first`, `scan_reexport_patch_target` and `scan_todo_markers` (the last is a legitimate re-export of `meta_test_utils.scan_todo_markers`, wrapped by the registered `todo_hygiene`). Their tests mask the gap by importing the function directly: `tests/test_assert_in_loop.py:11` does `from pyutilz.dev.code_audit import scan_assert_in_loop_reports_only_the_first`, never `get_scanners()`. `reexport_patch_target.py` is not redundant with the registered `patch_target_is_a_reexport` — the latter's own header comment (`patch_target_is_a_reexport.py:44`) scopes itself to string patch targets and says the attribute-form target "is resolved by a different rule", which is precisely the unregistered module.
- **Failure scenario**: a downstream project pins `pyutilz`, runs `python -m pyutilz.dev.code_audit ./src` expecting the advertised catalogue, and gets zero coverage of both defect classes. `--check assert_in_loop` is not even accepted: `argparse`'s `choices=sorted(get_scanners())` (cli.py:66) rejects the name outright, so there is no workaround short of importing the function by hand.
- **Suggested fix**: add `register_scanner("assert_in_loop_reports_only_the_first", scan_assert_in_loop_reports_only_the_first)` and `register_scanner("reexport_patch_target", scan_reexport_patch_target)` in `registry.py` (in `OPT_IN_ONLY` if their precision has not been measured on a real corpus), and add a meta-test asserting that every `scan_*` callable reachable from the package facade appears in `get_scanners().values()`.

### F05. [Medium] `ClaudeCodeToolUseError` is a seventh LLM exception defined outside `llm/exceptions.py`, so `except LLMProviderError` cannot catch it and the domain-root guard test does not see it — src/pyutilz/llm/claude_code_provider.py:31
- **Disposition**: COMPLETED — `ClaudeCodeToolUseError` moved to src/pyutilz/llm/exceptions.py:91 as `(LLMProviderError, RuntimeError)`, re-exported from `claude_code_provider` (src/pyutilz/llm/claude_code_provider.py:31) and from `pyutilz.llm` + its `__all__`; the guard was widened to a `pkgutil.walk_packages` sweep over each of the llm/database/web domains at tests/test_architecture_audit_20260903.py:88.
- **Category**: exception-hierarchy
- **Problem**: `llm/exceptions.py` defines six classes, all rooted at `LLMProviderError` (the 2026-09-02 F02 fix, re-verified). `claude_code_provider.py:31` defines a seventh, `class ClaudeCodeToolUseError(RuntimeError)`, in the provider module rather than the domain's exceptions module. It does not inherit `LLMProviderError`, is not re-exported from `pyutilz.llm`, and is not in `pyutilz.llm.__all__` — verified by grep (its only two occurrences in the whole tree are its definition and the `raise` at `claude_code_provider.py:583`). The guard test `tests/test_architecture_audit_20260902.py:94-101` iterates `vars(exceptions)` only, so an exception defined anywhere else in the domain is structurally invisible to it — the same holds for the `database` and `web` equivalents at `:124` and `:135`. A grep for exception classes outside any `exceptions.py` finds exactly three in the library: this one, `core/safe_pickle.py:138` and `system/resilience.py:158` (the latter two are dispositioned reachable via their packages' `__getattr__`, per 2026-09-02 F09).
- **Failure scenario**: a caller writes the documented catch-all `except LLMProviderError as e:` around `provider.generate(...)`. With the Claude Code provider selected and the model emitting a tool-use block, `ClaudeCodeToolUseError` propagates past that handler uncaught. The class's own docstring calls it "a security event to surface to the caller" — so the one error the design most wants surfaced is the one the domain's advertised handler misses. The caller also cannot import the name to catch it specifically without reaching into `pyutilz.llm.claude_code_provider`.
- **Suggested fix**: move the class into `llm/exceptions.py` as `class ClaudeCodeToolUseError(LLMProviderError, RuntimeError)` (keeping `RuntimeError` preserves the documented "not an OSError, so the retry arm does not swallow it" property), re-export it from `pyutilz.llm` and add it to `__all__`. Then strengthen the three domain-root guard tests to walk every module in the domain package via `pkgutil` looking for `BaseException` subclasses, not just `vars(exceptions)`.

### F06. [Medium] Thirteen scanner modules each re-implement "is this a test file" with six mutually incompatible definitions, and `_base.py` offers no shared helper — src/pyutilz/dev/code_audit/_base.py:56
- **Disposition**: COMPLETED — one `is_test_file(path, root, extra_test_globs)` in src/pyutilz/dev/code_audit/_base.py:196 (widest definition: name convention, `tests`/`test` path component, or a caller-supplied glob), and all thirteen call sites across the twelve scanner modules routed through it; the three private predicates (`_is_test_file`, `_looks_like_a_test_file`, `_is_test_path`) are gone, pinned by tests/test_architecture_audit_20260903.py:131.
- **Category**: shared-helper-reuse
- **Problem**: `_base.py` is the package's stated home for decisions made once (`_is_excluded`'s docstring at `:70-76` says so explicitly: "One implementation, called from every scanner that walks a tree, because three copies of this decision is how the bug it now prevents got in"). - **Failure scenario**: a project whose tests live in `tests/check_pricing.py` (no `test_` prefix, pytest configured with a custom `python_files`) is scanned by `spy_arity`, `lazy_log_assertion`, `accumulator_helper_bypassed`, `hardcoded_test_path` and `source_text_assertions`, and skipped entirely by `vacuous_assertions`, `skip_masking_except`, `measurement_hygiene`, `redundant_test_fit`, `patch_target_is_a_reexport` and `test_asserts_against_production_constant`. Half the test-focused catalogue silently reports nothing, with no error and no way for the user to tell coverage from cleanliness — the exact failure mode `_is_excluded`'s docstring documents ("359 findings and 0 findings, with no error either way").
- **Suggested fix**: add one `_is_test_file(path: Path) -> bool` to `_base.py` with the widest definition (prefix, `_test.py` suffix, or a `tests`/`test` path component) plus an optional `test_glob`/`test_dirs` parameter so a project with a custom layout can widen it once, and route all thirteen call sites through it. `vacuous_assertions.py:158` already threads a `test_glob` parameter, which is the right shape to lift.
