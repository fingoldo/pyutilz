# Performance Audit — pyutilz (2026-09-03)

## Summary

Scope: `src/pyutilz/dev/code_audit/**` (89 scanner modules, `_base.py`, `registry.py`), the total wall time of `tests/test_meta/`, and a sweep of the library hot paths named in the direction (`performance/kernel_tuning/**`, `system/gpu_dispatch.py`, json paths, regex-in-loop patterns).

Everything below is **measured** with `D:/ProgramData/anaconda3/python.exe` and `time.perf_counter`, using interleaved A/B loops (patched-vs-original in the same process, alternating, 2+ repeats) wherever a ratio is claimed. Scratch scripts live under `D:\Temp\perfaudit0903\`; no repo file was modified. Every proposed rewrite was verified to produce **identical findings** against the original before its timing was taken.

Machine caveats: Windows 10, **4 physical cores** (not the 16-core box the registry's tuning comments were measured on), not quiet. Absolute seconds drift 10-25% between whole-suite repeats — the first `run_all()` in a process reads ~40% higher than the third — so single-shot before/after numbers taken minutes apart are NOT trusted here, and every headline ratio comes from an alternating A/B inside one process. The low core count matters for the parallel numbers: `run_all(parallel=True)` gets 2-4 workers here, not 8+, so per-scanner fixed overheads weigh *more* in wall time than they would on a many-core CI runner, while `ProcessPoolExecutor` speedups weigh less.

Reference points measured for sizing:

* `run_all()` over `src/pyutilz` (242 files, 74 default scanners): **20.1-20.9 s** parallel, **~104 s** sequential, 174 findings.
* Full `tests/test_meta/` run: **195.5 s**, 185 passed / 4 skipped (`pytest -q --no-cov -p no:randomly --durations=25`).
* `_safe_parse`'s `_PARSE_CACHE` works as documented — a warm re-parse pass over 242 files costs 0.011 s against 0.927 s cold — so the 2026-09-02 wave's parse-cache work is NOT regressed and is not re-raised.

**Prior-wave verification (not re-raised):** F01's `synchronize_gpu=True` default is present in `kernel_tuning/benchmark.py` with the 1894x measurement recorded in its docstring; F09's per-process makedirs-once memo is present in `cache_base.py:226-238`; F04's `lru_cache` on the CUDA probe is present in `core/pythonlib/hardware.py:52`. The single `bench-attempt-rejected` marker in the repo (`data/pandaslib/frames.py:276`, polars rare-filter) is not touched by anything below.

Counts by severity: **1 Critical, 2 High, 3 Medium, 2 Low** (8 total).

## Findings

### F01. [Critical] `scan_vacuous_empty_pattern_match` slices function source for every function before checking whether the function can match — 54 s of a 195 s meta-suite run, 123x removable — src/pyutilz/dev/code_audit/vacuous_matching.py:58
- **Disposition**: COMPLETED � `ast.get_source_segment` per function replaced by a LAZY slice of the already-materialised `src_lines`, built only after the `all(...)` / comprehension / bare-`Name` filters have all passed (the module source is built lazily too). Re-measured on the rewritten package, warm, 3 repeats over `tests/`: 23.5 / 24.9 s before -> 0.65 / 0.67 s after, ~36x, with the SAME 7 findings at the same file:line (the report's 2 predate the wave's scanner fixes). The proposed `"all(" not in src` file gate was deliberately NOT added: `all (x for x in ys)` is valid Python, so the gate would introduce a silent false negative, and it buys nothing once the slice is lazy.
- **Category**: quadratic-source-slicing
- **Problem**: Line 58 runs `fn_src = ast.get_source_segment(src, fn) or ""` unconditionally for **every** `FunctionDef`/`AsyncFunctionDef` in every file, before the inner loop has established that the function contains even one `all(...)` call. `ast.get_source_segment` re-splits the whole file (`source.splitlines(True)`) on each call, so the cost is O(functions x file size) per file — quadratic in file size. Measured against `tests/` (187 files, 2.23 MB): the scanner takes **53.5 s** and is **94% of the entire 56.9 s** cost of the seven checks wired into `test_code_audit_tests_baseline.py`; the other six together cost 3.45 s. Moving the source slice behind the existing `all(...)`-call filter (compute `fn_src` lazily from the already-materialised `src_lines`, only once a bare-`Name` iterable is actually found) plus a one-line `if "all(" not in src: continue` file gate measured **54.02 s -> 0.441 s** and **52.79 s -> 0.474 s** across two alternating repeats — **111-123x** — with the same 2 findings at the same file:line.
- **Failure scenario**: `test_no_new_test_quality_findings_in_the_test_suite` is the slowest test in the repo at **55.50 s**, 28% of the whole `tests/test_meta/` wall (195.5 s), paid on every commit by the meta-test gate. It is also paid by every downstream consumer that opts this scanner in, and it grows quadratically with test-file size — a suite twice this size pays roughly four times as much. The check itself finds 2 baselined entries.
- **Suggested fix**: In `scan_vacuous_empty_pattern_match`, (a) skip a file outright when `"all("` is not in its source, and (b) initialise `fn_src = None` before the `for call in ast.walk(fn)` loop and build it (`"\n".join(src_lines[fn.lineno - 1 : fn.end_lineno or fn.lineno])`) only immediately before the `_is_guarded` call, i.e. after the `all(...)` / comprehension / bare-`Name` filters have all passed. Both changes are behaviour-preserving; the identical-findings check above covers them together. `partial_fix.py:75` has the same `get_source_segment`-in-a-loop shape but is bounded to sibling-family members, and `partial_fix.py:126` sits behind an early `if not filter_pairs: return []`, so neither needs the same treatment today.

### F02. [High] Every scanner re-walks the whole tree, and `_is_excluded` calls `Path.resolve()` twice per file — a 0.17 s walk repeated 74-89 times per run — src/pyutilz/dev/code_audit/_base.py:66-99
- **Disposition**: COMPLETED � `_iter_py_files` now uses a PRUNED `os.walk` that never descends into an excluded directory, instead of `rglob("*")` + `is_file()` + a per-file `_is_excluded` paying two `Path.resolve()` calls; nothing `os.walk` yields needs resolving to decide exclusion. 0.173 s -> 0.006 s per call over src/pyutilz's 248 files (~29x), verified to return the IDENTICAL path list in the identical order. No walk memo was added: pruning removes the cost outright, and a cross-call cache would hand a stale file list to the scanners' own tmp-tree edit-then-rescan tests.
- **Category**: repeated-filesystem-walk
- **Problem**: `_iter_py_files` is called fresh by each scanner (79 modules import the symbol), and it is far more expensive than it needs to be. Two separable causes: it uses `root.rglob("*")` + `p.is_file()` rather than `rglob("*.py")`, and `_is_excluded` (line 74) calls `path.resolve()` **and** `root.resolve()` for **every candidate file** — a syscall per file per scanner on Windows. Measured over `src/pyutilz` (242 files): `_iter_py_files` = **0.1734 s**; the same file list via `rglob("*.py")` with a component check and no `resolve()` = **0.0117 s**; via a pruned `os.walk` = **0.0052 s** — **15-33x**, same 242 paths. Component breakdown: `rglob("*")`+`is_file` 0.0249 s, `rglob("*.py")` 0.0079 s, `rglob("*.py")`+`resolve()` per file 0.0662 s. Whole-run A/B with a `(root, exclude_dirs)`-keyed walk cache patched into all 79 scanner modules, alternating in one process: sequential **53.70 vs 67.97 s** then **44.40 vs 55.90 s** (-21% both times); parallel `run_all` **17.87 / 17.26 s vs 20.10 / 20.44 / 20.89 / 20.77 s** (-14%), identical 174 findings every time.
- **Failure scenario**: 14-21% of every `run_all()` — about 3 s of the 19.6 s `test_no_new_code_audit_findings` on this 4-core box, and proportionally more on a many-core CI runner where the walk is a larger share of what parallelisation leaves behind. Every downstream consumer of `dev.code_audit` pays the same tax, and it scales with repo size: because of the `.claude/` worktree exclusion, `resolve()` runs on every file of every nested checkout before that file is rejected.
- **Suggested fix**: Two independent changes. (1) In `_iter_py_files`, iterate `root.rglob("*.py")` and do the exclusion check on `p.relative_to(root).parts` computed without `resolve()`, hoisting `root.resolve()` out of the loop — that preserves the relative-vs-absolute correctness fix the current code exists for. (2) Add a walk cache next to `_PARSE_CACHE`, keyed `(str(root), exclude_dirs)`. Key it so it survives the in-process tmp-tree rewrites the scanners' own unit tests do — either scope the cache to one `run_all()` invocation and pass it down, or key it on the root's `st_mtime_ns` the way `_PARSE_CACHE` keys on each file's; a plain permanent `(root, exclude_dirs)` memo would hand a stale file list to a test that creates a file and rescans.

### F03. [High] `test_individual_subpackages_import_no_network` spawns 13 interpreters serially — 14.6 s where 4.1 s suffices — tests/test_meta/test_no_top_level_side_effects.py:147
- **Disposition**: COMPLETED � the 13 `subprocess.run` spawns now run through `ThreadPoolExecutor(max_workers=8)` (threads, since each unit of work is already its own OS process and `subprocess.run` releases the GIL), with the same per-target timeout and the same failure text. Re-measured on this box: serial 15.15 s -> threaded 4.12 s, 3.7x, same 13 completed processes all returning 0; the test's own `--durations` entry went 14.7 s -> 4.24 s.
- **Category**: serial-subprocess-fanout
- **Problem**: The test loops `for target in _SUBPACKAGES_TO_PROBE: result = _run_with_targets([target])`, one `subprocess.run([sys.executable, "-c", script])` per subpackage, strictly serially. There are 13 targets and each spawn is a full interpreter start plus a package import; the work is child-process bound, so `subprocess.run` releases the GIL throughout and a plain thread pool parallelises it with no process-pool machinery. Measured: **serial 14.56 s**, `ThreadPoolExecutor(4)` **4.80 s**, `ThreadPoolExecutor(8)` **4.09 s** — **3.0-3.6x**, same 13 completed processes. `--durations` reports this test at 14.71 s, fourth-slowest in the suite.
- **Failure scenario**: ~10.5 s of the 195.5 s meta-suite wall on every commit, growing linearly as subpackages are added (the list is a hand-maintained roster of every optional-dep subpackage). On a CI runner with more cores the serial version does not get faster at all.
- **Suggested fix**: Replace the loop with `concurrent.futures.ThreadPoolExecutor(max_workers=min(8, len(_SUBPACKAGES_TO_PROBE)))` and `executor.map`, collecting `(target, result)` pairs and building the same `failures` list from those with a non-zero return code so the failure message stays byte-identical. Keep the per-target `timeout=60`. Threads, not processes: each unit of work is already its own OS process.

### F04. [Medium] `scan_comment_names_missing_symbol` tokenizes every file when only 11 of 242 can produce a hit — 2.3x on the scanner — src/pyutilz/dev/code_audit/comment_names_missing_symbol.py:71, 105-107
- **Disposition**: COMPLETED � the scanner now skips a file whose source carries no backticked citation at all (a comment/docstring is a substring of the source, so such a file cannot produce a finding), and `_comment_texts` gained a bounded `(path, mtime_ns, size)`-keyed memo so the two scanners calling it tokenize each file at most once per process. 1.87 / 1.84 / 1.82 s -> 0.572 / 0.569 / 0.571 s over src/pyutilz, 3.2x, identical 5 findings.
- **Category**: missing-cheap-prefilter
- **Problem**: `_comment_texts` runs a full `tokenize.generate_tokens` pass plus an `ast.walk` docstring sweep on **every** file, and the scanner then applies `_BACKTICKED_CALL` (a `` `_name()` `` citation) to the extracted text. But a comment or docstring is by construction a substring of the file source, so a file whose source does not match `_BACKTICKED_CALL` anywhere cannot produce a finding. Measured over `src/pyutilz`: only **11 of 242 files** contain such a citation at all; `_comment_texts` over all files costs **1.070 s** (of which `tokenize` alone is 0.783 s) against **0.058 s** when gated by `_BACKTICKED_CALL.search(source)` — **18x on that phase**. The scanner as a whole measures **1.770 s** for 2 findings; the gate removes ~1.01 s of it (~2.3x).
- **Failure scenario**: ~1 s of every default `run_all()` — this is the third-most-expensive scanner in the registry at 4.1% of the sequential total — for a check that fires twice. `_comment_texts` is also called uncached by `scan_comment_cites_absolute_line`, so a project that opts that check in re-tokenizes the whole corpus a second time.
- **Suggested fix**: Read the source once per file in `scan_comment_names_missing_symbol` (it already reads it for `src_lines`), `continue` when `_BACKTICKED_CALL.search(src)` is None, and pass the already-read text into `_comment_texts` instead of letting it re-read the file. Additionally give `_comment_texts` a `(path, mtime_ns, size)`-keyed memo in the same style as `_PARSE_CACHE`, so the two scanners that call it tokenize each file at most once per process.

### F05. [Medium] `scan_async_primitive_reinit_per_call` does an O(nodes x nested-def nodes) membership test inside its node loop — 1.8x — src/pyutilz/dev/code_audit/async_primitive_reinit.py:231
- **Disposition**: COMPLETED � `any(node in ast.walk(nested) for nested in nested_defs)` replaced by one `{id(n) for ...}` set built once per function, above the node loop. 4.05 / 3.80 / 3.80 s -> 2.44 / 2.26 / 2.20 s over src/pyutilz, 1.73x, identical findings (0 on this tree; the scanner's own unit tests cover the positive cases and pass).
- **Category**: quadratic-ast-membership
- **Problem**: `if any(node in ast.walk(nested) for nested in nested_defs): continue` re-walks **every** nested function definition, from scratch, for **every** node of the enclosing function — an O(len(func) x len(nested defs) x len(nested)) test where an O(len(nested)) precomputation suffices. Hoisting `_nested_ids = {id(n) for nd in nested_defs for n in ast.walk(nd)}` above the `for node in ast.walk(func)` loop and testing `id(node) in _nested_ids` measured **3.327 s -> 1.824 s** and **3.289 s -> 1.807 s** over `src/pyutilz` — **1.8x**, identical findings (0 on this tree). This is the only `x in ast.walk(y)` membership test in the package (grepped).
- **Failure scenario**: ~1.5 s of every default `run_all()`; by cold-run measurement this is the single most expensive scanner in the registry, 7.5% of the sequential total. The cost is quadratic in function size, so it is worst on exactly the large async orchestration functions the scanner exists to audit.
- **Suggested fix**: Precompute the nested-node id set once per function, immediately after `nested_defs` is built at line 227, and replace line 231 with a set membership test. `id()` is safe here because the tree keeps every node alive for the whole loop; a `set` of nodes would work too (`ast.AST` hashes by identity), and `id()` just makes that explicit.

### F06. [Medium] 82 scanner modules re-read and re-`splitlines()` files that `_safe_parse` has already read — 2-5% of a full run — src/pyutilz/dev/code_audit/_base.py:107-131 (and ~95 call sites, e.g. closures.py:170, broad_except.py:166, mutable_defaults.py:235)
- **Disposition**: COMPLETED � `_read_src_lines` (called from 77 of the scanner modules) is now memoised on `(path, mtime_ns, size)` alongside `_PARSE_CACHE`, with the same bound and the same in-process edit-then-rescan semantics, and `clear_parse_cache()` clears both. `vacuous_matching`'s direct `read_text` was routed through it as well. Measured together with F01/F02/F04/F05/F07 as a whole-run A/B, sequential `run_all()` over src/pyutilz: 50.34 / 51.65 s before -> 39.11 / 39.35 s after, -24%, 234 findings either way.
- **Category**: missing-cache
- **Problem**: `_safe_parse` caches the parsed tree but discards the source text it read to produce it. Every scanner that wants a snippet then does its own `py.read_text(encoding="utf-8", errors="replace").splitlines()` — 82 modules, ~95 call sites. Measured: one read+splitlines pass over the 242 files of `src/pyutilz` costs **0.0596 s** warm, so roughly 4.9 s of the ~104 s sequential run is re-decoding text the parse cache already had in hand. Interleaved A/B with a memo patched over `Path.read_text` (which still leaves the `splitlines()` work in place): **48.21 vs 50.73 s (-5.0%)** then **46.88 vs 47.68 s (-1.7%)**. A cache that returns the split line list, not just the text, removes more than this A/B measured.
- **Failure scenario**: A few percent of every `run_all()` and of every meta-test that drives one, on every commit, plus 242 redundant file reads per scanner-process. It is a straight duplicate of I/O the process has already done, and it grows with both file count and scanner count.
- **Suggested fix**: Add `_source_lines(path) -> list[str]` (and/or `_source_text`) to `_base.py`, memoised on `(str(path), st_mtime_ns, st_size)` exactly like `_PARSE_CACHE` so the same in-process edit-then-rescan semantics hold, and have `_safe_parse` populate it with the text it already read. Converting the call sites is mechanical — `_line_text` already takes the resulting list unchanged.

### F07. [Low] `scan_possibly_dead_import` makes two full-corpus AST walks that fuse into one — 0.34 s, 29% of the scanner — src/pyutilz/dev/code_audit/dead_import.py:138-147, 158-169
- **Disposition**: COMPLETED � both full-corpus walks fused into one `_corpus_import_index(root, exclude_dirs)` that dispatches on node type in a single pass; `_attribute_names_in_corpus` and `_from_import_names_by_file` stay as thin wrappers so each keeps its own false-positive-class explanation. Scanner total 1.147 / 1.178 / 1.165 s -> 0.807 / 0.843 / 0.805 s over src/pyutilz, -30%, identical 2 findings.
- **Category**: redundant-ast-walk
- **Problem**: `_attribute_names_in_corpus` and `_from_import_names_by_file` each iterate the whole file list and `ast.walk` every (parse-cached) tree, collecting `ast.Attribute` names and `ast.ImportFrom` names respectively; both are called back-to-back at the top of the scanner. Measured over `src/pyutilz`: two walks **0.726 s**, one fused walk collecting both **0.385 s** — a 0.34 s saving on a scanner that costs 1.187 s in total (29%), with both returned structures verified identical. (The nearby `_is_consumed_by_another_files_from_import`, which reads as O(files) per candidate, was instrumented and fires only **38 times** on this tree — not worth changing, and stated here so a later audit does not re-open it.)
- **Failure scenario**: ~0.3 s per `run_all()`, and the same ~0.3 s in every downstream consumer's commit gate. Small in isolation; comfortably above the 0.5%-of-run bar for this scanner.
- **Suggested fix**: Replace the two call sites with one private `_corpus_import_index(root, exclude_dirs) -> tuple[set[str], dict[Path, set[str]]]` that walks each tree once and dispatches on node type in a single `isinstance` chain. Keep the two existing helpers as thin wrappers if their docstring prose is worth preserving separately.

### F08. [Low] `_require_usable_bash()` re-probes WSL once per test instead of once per session — tests/test_meta/test_publish_workflow_version_check.py:53, called from :57
- **Disposition**: COMPLETED � the WSL probe was split into an `lru_cache(maxsize=1)`-wrapped `_bash_can_read_repo() -> bool`, with `_require_usable_bash()` raising the skip from that cached boolean (a cached function that itself raised `Skipped` would memoise nothing). The probe subprocess now runs once per session instead of once per test: the three skipping tests went from a ~0.17 s probe each to 0.02 / 0.02 / 0.01 s total.
- **Category**: missing-cache
- **Problem**: `_run_check_script` calls `_require_usable_bash()`, which spawns `bash -c '...'` with `timeout=30`; three tests call it and the probe's answer cannot change within a session. Measured on this box: the first probe costs **13.31 s** (cold WSL start), subsequent identical probes **0.17 / 0.17 / 0.19 s** — so caching saves ~0.5 s here. The 13.3 s first call is real but not removable by caching; it is what makes `test_matching_tag_and_version_passes` the second-slowest test in the suite at 22.92 s on a run where the other three then **skipped**.
- **Failure scenario**: ~0.5 s per meta-suite run on Windows, plus two redundant WSL spawns. On a host where the probe times out rather than failing fast, the same cache turns a 3 x 30 s worst case into a single 30 s one.
- **Suggested fix**: Split the probe into an `lru_cache(maxsize=1)`-wrapped function returning a bool (or the skip reason / None), and have `_require_usable_bash()` call `pytest.skip(...)` from that cached result — the skip must still raise per test, but the subprocess then runs once. Caching a function that itself raises `Skipped` would not memoise the outcome, so the boolean split is load-bearing.
