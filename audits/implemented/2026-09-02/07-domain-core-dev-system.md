### F01. [High] `DiskCache` LRU eviction destroys the MOST-recently-used entry, because `get()` touches the payload but never its sidecar — src/pyutilz/core/disk_cache.py:322
- **Disposition**: COMPLETED — eviction now treats (payload, sidecar) as one indivisible entry and get() touches both mtimes: src/pyutilz/core/disk_cache.py:322-330, :396-461. Regression: tests/test_disk_cache_audit_regression.py::test_hot_entry_survives_eviction_with_its_sidecar
- **Category**: cache-correctness
- **Problem**: `get()` refreshes only `<key>.pkl`'s mtime (`os.utime(path, None)`, line 322). The companion `<key>.pkl.sha256` written by `write_sidecar` at line 361 keeps its original put-time mtime forever. `_evict_if_needed` (lines 378-405) scans every non-`tmp_` file in `cache_dir` as an independent LRU candidate sorted by mtime (line 394), so for any frequently-read key the sidecar is among the OLDEST files in the directory and is evicted first. `get()` then calls `safe_load`, which fails CLOSED on a missing sidecar (`safe_pickle.verify_sidecar` lines 183-202), the `PickleVerificationError` branch at line 305 fires, and `_drop_corrupt_entry` deletes the surviving payload too (line 311). The `protect=` argument (line 398) protects only the payload path of the entry just written, never any sidecar.
- **Failure scenario**: Reproduced. `DiskCache(d)` with three 30 KB entries `hot`/`cold1`/`cold2` written in that order; `c.get("hot")` is then called (payload mtime becomes the newest in the directory, sidecar mtime stays the oldest); `max_size_bytes` is lowered to 62000 and `_evict_if_needed()` runs. Directory afterwards: `['cold1.pkl.sha256', 'cold2.pkl', 'cold2.pkl.sha256', 'hot.pkl']` — `hot.pkl.sha256` gone. The next `c.get("hot")` logs `verify_sidecar: no .sha256 sidecar ... refusing to load`, returns `None`, and deletes `hot.pkl`, leaving `['cold1.pkl.sha256', 'cold2.pkl', 'cold2.pkl.sha256']`. The hottest entry was evicted, both cold entries' payload/sidecar pairing was also broken, and the class docstring's "LRU eviction by file mtime" contract is inverted for exactly the keys LRU exists to keep.
- **Suggested fix**: Treat `(payload, sidecar)` as one indivisible cache entry: in `_evict_if_needed`, skip `*.sha256` files when building the candidate list, attribute their size to the owning payload entry, and unlink both when evicting; in `get()`, `os.utime` the sidecar alongside the payload.

### F02. [High] `DiskCache.put` leaks an orphan `tmp_*.pkl` (invisible to the size cap forever) and raises out of a method documented not to, whenever pickling raises `TypeError` — src/pyutilz/core/disk_cache.py:364
- **Disposition**: COMPLETED — put() catches Exception (not just OSError/PicklingError) and unlinks tmp_ in a finally, so an unpicklable payload can neither escape nor strand a file: src/pyutilz/core/disk_cache.py:377-394. Regression: tests/test_disk_cache_audit_regression.py::test_put_of_unpicklable_value_leaves_no_orphan_tmp_file
- **Category**: resource-leak
- **Problem**: The `except (OSError, pickle.PicklingError)` clause at line 364 does not cover `TypeError`, which is what CPython raises for the most common unpicklable payloads (`cannot pickle '_thread.lock' object`, sockets, generators, open file handles). Those escape the handler, so the `tmp_path.unlink()` cleanup at line 367 never runs and the temp file stays. `_evict_if_needed` (line 382) and `total_size` (line 429) both skip names starting with `tmp_`, so the orphan is never evicted and never counted against `max_size_bytes` — it accumulates until the disk fills. `put`'s docstring documents no raising behaviour at all.
- **Failure scenario**: Reproduced. `DiskCache(d).put("lock", threading.Lock())` raises `TypeError: cannot pickle '_thread.lock' object` out of `put`; afterwards `os.listdir(d) == ['tmp_23d7b5c23d124ce6ba5ae60dfe43a14b.pkl']` while `c.total_size() == 0`. In a caching layer over an ML pipeline (its stated purpose) any value that transitively holds a lock/handle produces one permanent orphan file per call.
- **Suggested fix**: Broaden the handler to `except Exception` (or at minimum add `TypeError`/`AttributeError`/`RecursionError`), always unlink `tmp_path` in a `finally`, and either sweep stale `tmp_*` files in `_evict_if_needed` or stop excluding them from `total_size`.

### F04. [High] `sweep_backend_crossover` silently disables its own correctness gate — a divergent backend is picked as the winner whenever the reference variant raises — src/pyutilz/dev/benchmarking.py:186
- **Disposition**: COMPLETED — a raising reference variant now logs at WARNING and skips the size/combination instead of emitting an ungated max_abs_diff of 0.0, in both sweep_backend_crossover and sweep_backend_grid: src/pyutilz/dev/benchmarking.py:186-192, :441-447. Regression: tests/test_dev_audit_fixes.py::test_sweep_skips_a_size_whose_reference_variant_raises
- **Category**: silent-error-swallow
- **Problem**: Lines 183-187 wrap the reference call in `try: ref_out = variants[ref](*args) ... except Exception: ref_out = None` with no logging at any verbosity. Line 207 then computes `diff = 0.0 if (name == ref or ref_out is None) else _max_abs_diff(ref_out, out)`, so with `ref_out is None` every candidate gets `diff = 0.0` and passes the gate at line 209 unconditionally. The function's own docstring for the `reference` parameter states the opposite guarantee: "others must match within tol or they are disqualified at that size (SURFACES a divergent-but-faster variant instead of silently picking it)". The resulting region dicts are the documented input to `kernel_tuning_cache`, so a wrong backend gets persisted as a tuned decision.
- **Failure scenario**: `sweep_backend_crossover({"numpy": np_fn, "cupy": cp_fn}, sizes=[10_000], make_inputs=mk, primary_axis="n")` on a host where the reference `numpy` variant raises at that size (e.g. `MemoryError`, or a shape assumption that holds only for the GPU path). The except swallows it, `ref_out=None`, `cupy` records `diff=0.0`, survives the gate, wins the timed rank, and the emitted region is `{"n_max": None, "backend_choice": "cupy", "max_abs_diff": 0.0}` — a `max_abs_diff` of `0.0` that was never measured against anything.
- **Suggested fix**: On a reference-variant exception, log it (at WARNING, not gated on `verbose`) and skip the size entirely — or mark the size's region as ungated rather than emitting a fabricated `max_abs_diff: 0.0`. Never let `ref_out is None` mean "everything is equivalent".

### F06. [Medium] `hash_object` produces a different cache key for the same `frozenset` in every process — `frozenset` falls through to the unstable `repr()` last resort — src/pyutilz/core/disk_cache.py:191
- **Disposition**: COMPLETED — frozenset takes the sorted-by-repr stable path with its own tag byte: src/pyutilz/core/disk_cache.py:179-184. Regression: tests/test_disk_cache_audit_regression.py::test_hash_object_frozenset_stable_across_hash_seeds
- **Category**: cache-correctness
- **Problem**: `_feed` handles `set` explicitly at line 179 (sorted by `repr` for stability) but `frozenset` is NOT a subclass of `set`, so it reaches the "Last resort: repr() the object" branch at lines 191-195. `repr` of a frozenset iterates in hash order, which depends on `PYTHONHASHSEED` and is therefore different in every process. The module docstring's core promise is "Content-addressable, NOT path-keyed. Two processes writing the same key end up with bit-identical bytes", and `compose_key`/`hash_object` are named in `_key_path`'s docstring as the safe key producers.
- **Failure scenario**: Reproduced. `hash_object(frozenset(['alpha','beta','gamma','delta']))` run in six subprocesses with `PYTHONHASHSEED` 0..5 yields six distinct digests. A caller keying on a frozenset of feature names (`compose_key(hash_array_summary(X), hash_object({"features": frozenset(cols)}))`) gets a 0% hit rate across worker processes and writes one cache file per worker — silently defeating the cache and filling it to the eviction cap with duplicates of the same value.
- **Suggested fix**: Change line 179 to `isinstance(obj, (set, frozenset))` with a distinct tag byte for each, so both take the sorted-by-`repr` stable path.

### F07. [Medium] `CircuitBreaker` opens on failures that were never consecutive, while logging "OPEN after N consecutive failures" — src/pyutilz/system/resilience.py:231
- **Disposition**: COMPLETED — CircuitState gained an explicit is_half_open flag; a CLOSED success resets failure_count, the half_open_max_calls success run applies only while genuinely HALF_OPEN, and a failed probe re-opens at once: src/pyutilz/system/resilience.py:167-171, :218-262. Regression: tests/test_system_audit_fixes.py::test_circuit_stays_closed_under_alternating_failures
- **Category**: state-machine-correctness
- **Problem**: On a successful call, lines 231-238 reset `failure_count` to 0 only via the `else` branch (where it is already 0), or after `half_open_max_calls` accumulated successes in the `if` branch. So while `failure_count > 0` — i.e. in ordinary CLOSED operation after a single sporadic failure — successes do NOT clear the counter until `half_open_max_calls` of them have accumulated. `failure_count` is therefore a running total, not a consecutive count, but line 250 logs `"Circuit %s OPEN after %d consecutive failures"` and the class docstring says "OPEN: too many consecutive failures". Whenever `half_open_max_calls > failure_threshold`, a steady-state partial-failure workload trips the breaker.
- **Failure scenario**: Reproduced. `CircuitBreaker("t", failure_threshold=5, half_open_max_calls=10)` driven with strictly alternating failure/success (never two failures in a row, 50% success rate) raises `CircuitOpenError` on call 9, with final state `failure_count=5, half_open_successes=4, total_calls=9, total_failures=5` and the log line `Circuit t OPEN after 5 consecutive failures`. A service degraded to 50% availability is cut off entirely rather than half-served, and the operator log states a fact that never happened.
- **Suggested fix**: Track CLOSED/HALF_OPEN as an explicit state rather than inferring it from `failure_count > 0`; in CLOSED, reset `failure_count = 0` on any success. Apply the `half_open_max_calls` success-run requirement only while the state is genuinely HALF_OPEN.

### F08. [Medium] `count_trailing_zeros` counts the integer part's zeros too — the decimal separator increments a counter but does not stop the scan — src/pyutilz/core/pythonlib.py:398
- **Disposition**: COMPLETED — the reverse scan breaks at the decimal separator and the unused nseps accumulator is gone: src/pyutilz/core/pythonlib.py:398-418. Regression: tests/test_core_audit_fixes.py::test_count_trailing_zeros_ignores_integer_part
- **Category**: numeric-correctness
- **Problem**: The reverse scan at lines 407-414 treats any char in `",.e+-"` as a separator that increments `nseps` and then FALLS THROUGH to the next iteration instead of breaking. `nseps` is computed and never used (lines 405, 409). So after consuming the fractional zeros the loop keeps walking backwards into the integer part and keeps counting its zeros as if they were trailing fractional zeros. The function name and its only docstring example (`count_trailing_zeros(1.30e-6, precision=8) -> 1`) both describe fractional trailing zeros.
- **Failure scenario**: Reproduced. `count_trailing_zeros(100.0, precision=5)` returns `7` (format string `"100.00000"`: five fractional zeros plus the two zeros of `100`), expected `5`. `count_trailing_zeros(1000, precision=3)` returns `6`, expected `3`. Any caller using this as a "how many significant fractional digits does this price/measurement actually carry" heuristic mis-classifies every round number, and the error scales with the magnitude of the integer part.
- **Suggested fix**: `break` on the separator (or scan only `num_str.split(".")[-1]`), and drop the unused `nseps` accumulator.

### F11. [Medium] `TomlLiveConfig` crashes the pipeline it promises never to crash, on any `OSError` that is not `FileNotFoundError` — src/pyutilz/system/config.py:99
- **Disposition**: COMPLETED — _reload() catches OSError around read_bytes() and _maybe_reload() catches OSError around stat(), both keeping the previous data and warning: src/pyutilz/system/config.py:111-119, :146-153. - **Disposition**: COMPLETED — all mappings share one process-wide directory keyed by file_name, created once under a lock and logged at INFO: src/pyutilz/system/parallel.py:34-40, :272-300. Regression: tests/test_system_audit_fixes.py::test_mem_map_array_reuses_one_temp_directory
- **Category**: resource-leak
