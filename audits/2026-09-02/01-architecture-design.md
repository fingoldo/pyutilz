### F01. [High] `OpenAIProvider` is missing from `pyutilz.llm`'s public surface while every sibling provider is exported — src/pyutilz/llm/__init__.py:6
- **Disposition**: OPEN
- **Category**: api-surface-drift
- **Problem**: `llm/factory.py:77-85` (`_PROVIDER_MODULES`) lists seven providers including `"openai": ("pyutilz.llm.openai_provider", "OpenAIProvider")`, and `get_llm_provider`'s docstring advertises `"openai" / "gpt"` (`llm/factory.py:114`). The package facade keeps a **second, independent** map — `_LAZY_IMPORTS` at `llm/__init__.py:6-18` — plus an `__all__` at `llm/__init__.py:35-50`. Both omit `OpenAIProvider`. Every other concrete provider class (`AnthropicProvider`, `GeminiProvider`, `DeepSeekProvider`, `XAIProvider`, `OpenRouterProvider`, `ClaudeCodeProvider`) is present in both. The same duplication also drops four of the six LLM exception types: `llm/__init__.py:2` eagerly re-exports only `LLMProviderError` and `JSONParsingError`, while `LLMRefusalError`, `LLMSafetyBlockError`, `LLMTruncationError` and `LLMUnparseableResponseError` (`llm/exceptions.py:21,35,45,61`) are reachable only via the submodule path.
- **Failure scenario**: Verified live — `import pyutilz.llm as L` then `L.AnthropicProvider` resolves to `<class 'pyutilz.llm.anthropic_provider.AnthropicProvider'>`, `L.XAIProvider` resolves, but `L.OpenAIProvider` raises `AttributeError: module 'pyutilz.llm' has no attribute 'OpenAIProvider'`. A user who read the factory docstring and wrote `from pyutilz.llm import OpenAIProvider` by symmetry with the DeepSeek/xAI examples gets an ImportError at collection time, even though `get_llm_provider("openai")` works and the class exists at `llm/openai_provider.py`. Because the two maps are hand-maintained duplicates, adding provider #8 will drift the same way.
- **Suggested fix**: Add `"OpenAIProvider": ("pyutilz.llm.openai_provider", "OpenAIProvider")` to `_LAZY_IMPORTS` and to `__all__`, plus the four missing exception names; then remove the duplication by deriving `_LAZY_IMPORTS`'s provider entries from `factory._PROVIDER_MODULES` (or vice versa) so a single table drives both, and add a meta-test asserting every value of `_PROVIDER_MODULES` is reachable as an attribute of `pyutilz.llm`.

### F02. [High] Two of the six LLM exception types bypass the `LLMProviderError` root, so `except LLMProviderError` cannot catch all LLM errors — src/pyutilz/llm/exceptions.py:15
- **Disposition**: OPEN
- **Category**: exception-hierarchy
- **Problem**: `LLMProviderError(Exception)` (`llm/exceptions.py:6`) is the domain root; `LLMRefusalError` (`:21`), `LLMSafetyBlockError` (`:35`) and `LLMUnparseableResponseError` (`:61`) correctly derive from it. But `JSONParsingError(ValueError)` (`:15`) and `LLMTruncationError(ValueError)` (`:45`) derive from `ValueError` only. Verified live: `issubclass(JSONParsingError, LLMProviderError)` -> `False`; `issubclass(LLMTruncationError, LLMProviderError)` -> `False`. `LLMUnparseableResponseError`'s own docstring (`:61-72`) explicitly frames itself as the counterpart of `JSONParsingError`, yet the two sit in disjoint branches of the hierarchy. The same absence of a catchable root repeats in the sibling domains created to "mirror `pyutilz.llm.exceptions`'s pattern": `database/exceptions.py:11,20` (`RuntimeError` and `ValueError`, no shared base) and `web/exceptions.py:11,15` (both `RuntimeError`, no shared base).
- **Failure scenario**: A caller writes the natural catch-all around an LLM call — `try: provider.generate(...)` / `except LLMProviderError as e: fallback()`. A truncated generation raises `LLMTruncationError` and a malformed model JSON body raises `JSONParsingError`; neither is caught, both escape as a bare `ValueError` past a handler the type hierarchy promised would cover them, killing the request instead of triggering the retry/fallback the exceptions' own docstrings prescribe ("Retryable — caller should double `max_tokens`", `:48`).
- **Suggested fix**: Make `JSONParsingError` and `LLMTruncationError` inherit from both (`class JSONParsingError(LLMProviderError, ValueError)`) so existing `except ValueError` call sites keep working while `except LLMProviderError` becomes complete. Apply the same pattern per domain: add a `DatabaseError(Exception)` / `WebError(Exception)` root in `database/exceptions.py` and `web/exceptions.py` and reparent the existing classes, retaining the original builtin as a second base.

### F03. [Medium] `pyutilz.stats` and `pyutilz.performance` are invisible from the package facade — `pyutilz.stats` raises AttributeError — src/pyutilz/__init__.py:9
- **Disposition**: OPEN
- **Category**: package-boundary
- **Problem**: `src/pyutilz/__init__.py:9` declares `__all__ = ["__version__", "core", "data", "database", "web", "cloud", "text", "system", "dev", "llm"]` and the lazy `__getattr__` at `:76` hardcodes the identical 9-name tuple. The tree contains **eleven** subpackages: those nine plus `stats/` and `performance/`. Neither is in `__all__`, in the `__getattr__` tuple, or in `_MODULE_ALIASES` (`:13-41`, 27 entries). Both are shipped (`pyproject.toml:343`, `include = ["pyutilz*"]`) and `stats` even has its own extras group (`pyproject.toml:281`).
- **Failure scenario**: Verified live — `import pyutilz; pyutilz.stats` raises `AttributeError: module 'pyutilz' has no attribute 'stats'`, and `pyutilz.performance` raises the same, while `pyutilz.core` resolves. A user following the pattern every other subpackage supports hits an AttributeError for two real, installed, extras-declared subpackages; `from pyutilz import stats` happens to work only through Python's submodule-import fallback, so the two access styles disagree for exactly these two names and nowhere else.
- **Suggested fix**: Add `"stats"` and `"performance"` to `__all__` at `:9` and to the tuple at `:76`. Better: derive that tuple from `__all__` (or from `pkgutil.iter_modules(__path__)`) so subpackage #12 cannot be forgotten, and add a meta-test asserting every directory under `src/pyutilz/` containing an `__init__.py` is reachable as `getattr(pyutilz, name)`.

### F05. [Medium] A general-purpose library hardcodes the downstream project name `mlframe` as the default package of two public functions — src/pyutilz/performance/kernel_tuning/registry.py:209
- **Disposition**: OPEN
- **Category**: layering-violation
- **Problem**: `def discover_tuners(package: str = "mlframe", warn_on_import_fail: bool = True)` (`registry.py:209`) and `def retune_all(package: str = "mlframe", ...)` (`registry.py:248-249`) default their scan target to a specific downstream consumer that is not a dependency of pyutilz and appears nowhere in `pyproject.toml`. The module docstring codifies the same coupling: "Discovery walks the mlframe package" (`registry.py:5-6`). The failure path is silent by construction — `registry.py:226-230` catches the `ImportError` from `importlib.import_module("mlframe")`, logs it, and returns the (empty) existing `_REGISTRY` rather than raising.
- **Failure scenario**: Any consumer other than mlframe that installs `pyutilz` and calls `retune_all()` or `discover_tuners()` with the documented no-argument form gets one `logger.error("Failed to import package 'mlframe'")` line and an empty `{}` back — never an exception. `retune_all` then reports zero kernels tuned, and the caller's kernels silently keep using their `fallback` decisions forever, with the only evidence being an ERROR log naming a package the user has never heard of.
- **Suggested fix**: Make `package` a required positional parameter (no default) on both functions, or default it to the caller's own top-level package resolved via `inspect.stack()`/`__name__`; update the module docstring at `:5-6` to describe the contract generically. If a default must remain for mlframe's CLI convenience, put it in mlframe's own entry point (`mlframe-tune-kernels`, referenced at `performance/kernel_tuning/cache/cache_class.py:821`), not in the library.

### F06. [Medium] Five modules exceed the project's 1000-LOC split threshold, two of them flat siblings of already-split packages — src/pyutilz/text/similarity.py:1
- **Disposition**: OPEN
- **Category**: module-size
- **Problem**: Measured with `wc -l` over `src/pyutilz` (42,208 LOC total): `text/similarity.py` 1421 LOC / 32 defs; `database/db/__init__.py` 1212 / 40; `data/polarslib.py` 1091 / 17; `performance/kernel_tuning/cache/cache_class.py` 1085 / 39; `web/web.py` 1004 / 23. This repo has already executed this split twice, with the pattern documented in-file: `system/system/__init__.py:1` ("split from a 2024-LOC monolith") into six submodules, and `text/strings/__init__.py:35-36` ("subpackage split of the former 1070-LOC strings.py"), plus `data/pandaslib/`. The five above were left. Two are direct siblings of already-split packages, producing structural asymmetry inside one domain: `data/pandaslib/` is a 5-module package while `data/polarslib.py` is a 1091-LOC flat file; `text/strings/` is a package while `text/similarity.py` is a 1421-LOC flat file. Neither the 2026-07-21 full audit nor round 2 raised module size at all.

Keep every existing import path working via `__init__` re-export, as both prior splits did.

### F07. [Medium] `pyutilz.text.strings` star-exports `pd`, `np` and six stdlib modules, forcing an unused pandas+numpy import into a text subpackage — src/pyutilz/text/strings/__init__.py:21
- **Disposition**: OPEN
- **Category**: uncurated-star-export
- **Problem**: `text/strings/__init__.py:21` does `import pandas as pd, numpy as np` under a comment reading "Normal Imports (kept for public-surface backward compatibility)" (`:16-18`). Verified by grep over the whole 165-line file: `pd` and `np` each appear in exactly two places — the import at `:21` and the `__all__` entry at `:126`. They are never used. `__all__` (`:122-165`) deliberately exports the third-party aliases `"pd", "np"` alongside the stdlib names `"string", "json", "OrderedDict", "unicodedata", "re", "math", "defaultdict", "deque", "Counter"` (`:126-127`). The 2026-07-21 audit flagged this line as an *undeclared dependency*; that half was resolved by promoting pandas/numpy to core deps (`pyproject.toml:66,84`). The API-surface half was not, and is what remains open.

Independently, `import pyutilz.text.strings` costs 1.64 s measured on this box, essentially all of it pandas+numpy import, for a pure string-manipulation module that uses neither.
- **Suggested fix**: Drop `"pd", "np"` and the stdlib names from `__all__` at `:126-127` and delete the unused import at `:21`. If the names must stay resolvable for backward compatibility, expose them through a module-level `__getattr__` so they are reachable by attribute access without being star-imported and without importing pandas at module load. Then point the repo's own `uncurated_star_export` scanner (`dev/code_audit/uncurated_star_export.py`) at `src/pyutilz` in CI — it currently reports 0 precisely because this `__all__` is explicit.

### F11. [Low] Two different, mutually undocumented solutions to the same package/submodule circular-import problem — src/pyutilz/data/pandaslib/frames.py:25
- **Disposition**: OPEN
- **Category**: pattern-inconsistency
- **Problem**: Tarjan SCC over the module import graph returns exactly two strongly-connected components, both an already-split package's `__init__` mutually importing its own submodules: `{pyutilz.text.strings, ._logproxy, .basics, .configfiles, .jsonutils, .webtext}` and `{pyutilz.data.pandaslib, .benchmarks, .frames, .io_ops}`. The two packages solve it differently. `text/strings` introduced a dedicated indirection module, `_logproxy.py`, which does the parent import lazily inside a property (`text/strings/_logproxy.py:23`, commented "lazy: avoids import cycle at submodule load time"), and submodules import only `from ._logproxy import logger`. `data/pandaslib` instead does an eager top-level `import pyutilz.data.pandaslib as _facade` in three submodules (`frames.py:25`, `io_ops.py:19`, `benchmarks.py:29`), each with its own one-line "patchable-name indirection" comment. - **Failure scenario**: The `_facade` form works only because `import x` (unlike `from x import y`) binds the partially-initialised `sys.modules` entry — correct today, but silently order-dependent: any future `from pyutilz.data.pandaslib import HAS_IPYTHON` written at `frames.py` top level (the obvious refactor, and the form `text/strings` submodules actually use for their shared name) raises `ImportError: cannot import name ... (most likely due to a circular import)`, and nothing in the file explains why the awkward `_facade` spelling is load-bearing beyond "patchable-name indirection".
- **Suggested fix**: Pick one idiom. Either give `pandaslib` a `_facade.py` proxy mirroring `text/strings/_logproxy.py`, or document at both sites (and in `CLAUDE.md`'s monolith-split convention) that eager `import <parent> as _facade` is the project's chosen form and that `from <parent> import name` is forbidden inside a re-export package's submodules.

### F12. [Low] Two 25-line numba kernels are 99% identical, differing only in `range` vs `nb.prange` — src/pyutilz/text/similarity.py:1152
- **Disposition**: OPEN
- **Category**: duplicated-logic
- **Problem**: The repo's own `near_duplicate_function_body` scanner, run against `src/pyutilz`, returns exactly one finding: `_sentences_similarity_batch_with_matches_parallel` (`similarity.py:1152`) is 99% structurally similar to `_sentences_similarity_batch_with_matches_core` (`similarity.py:1124`). Read in full, the two 25-line bodies are identical except for the loop header (`for c in range(n_candidates)` vs `for c in nb.prange(n_candidates)`). The same duplication exists one pair up: `_sentences_similarity_batch_core` (`:1092`) vs `_sentences_similarity_batch_parallel` (`:1112`) — four kernels, two duplicated bodies. Same for the `:1092`/`:1112` pair.

### F13. [Low] `code_audit` exposes the mutable `SCANNERS` dict as public API alongside the read-only accessor its own docstring says to prefer — src/pyutilz/dev/code_audit/registry.py:69
- **Disposition**: OPEN
- **Category**: encapsulation
- **Problem**: `registry.py:69` defines `SCANNERS: dict[str, Callable[..., list[Finding]]] = {}` as a module-level public name, and `get_scanners()` at `:191-195` returns `dict(SCANNERS)` with a docstring stating "prefer this over importing `SCANNERS` directly when you only need to read the registry, so an accidental mutation (`get_scanners().pop(...)`) can't corrupt the shared dict for every subsequent `run_all()` call in the same process." Despite that, `SCANNERS` is reachable on the package facade — verified live, `pyutilz.dev.code_audit.SCANNERS` resolves to the live mutable dict and is one of only two registry-related names there, alongside `run_all`. Registration is otherwise properly gated by `register_scanner(..., allow_override=False)` (`:72-81`), which raises `ValueError` on a duplicate name — a guard that direct `SCANNERS[name] = fn` assignment bypasses entirely. The sibling registry does this correctly: `performance/kernel_tuning/registry.py:33` keeps `_REGISTRY` private and exports only `get_registry` in `__all__` (`:24-31`).
- **Failure scenario**: A consumer that does `from pyutilz.dev.code_audit import SCANNERS` then `SCANNERS.pop("mutable_default")` to skip one check permanently removes it for every later `run_all()` in the same process — no error, no restore path short of re-import. - **Suggested fix**: Rename to `_SCANNERS`, drop it from the package facade's re-exports, and route every read through `get_scanners()` and every write through `register_scanner()` — matching `performance/kernel_tuning/registry.py:33`'s already-correct encapsulation. Keep a deprecated module-level `__getattr__("SCANNERS")` returning a copy for one release if downstream code reads it.
